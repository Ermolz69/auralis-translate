# PERF-03: inference journal finish latency

Frozen before new probes on 14 October 2026. Baseline is `587789e` (PERF-02).
The question is which part of `journal_finish` explains its 7B partial-run
11.288 s / 54 operations, and whether a storage-only change reduces that cost
without changing durable acceptance or the translation policy. Failed attempts
and baseline binaries remain in ignored private experiment storage.

## Sequence and budget

First add opt-in monotonic timings for mutex wait, immediate-transaction begin,
row read/validation, UPDATE and COMMIT. Capture `journal_mode`, `synchronous`,
`wal_autocheckpoint`, page size, busy timeout, WAL size/header observations and
any detected WAL reset. Timing and WAL observations are private per-operation
records; publish aggregates only. Do not call a checkpoint pragma during timed
operations. WAL-file reads are opt-in for a diagnostic pass and timed separately
so their observer overhead cannot be mistaken for SQLite latency. Examine the
retained PERF-02 database read-only without migration.

Run three fresh deterministic fixture baselines, then two fresh real 7B local
baselines. If a cause is supported and a minimal candidate is justified, retain
the instrumented baseline executable, make one storage-only change, and run the
paired order candidate, baseline, baseline, candidate on fresh real files, plus
three fresh candidate fixtures. The original two baseline real runs are diagnostic,
not pooled with the later pair. Disclose time/order and cache uncertainty.

Each real run allows at most 32 chat requests, 128 count/preflight requests,
10 minutes and no automatic translation retry. Each fixture run allows 54
finishes and 2 minutes. The full experiment allows 45 minutes of probe wall time;
stop on identity mismatch, source mutation, exceeded budget, unrecoverable
infrastructure failure or failed durability check. Retain all failures as such.
No more than one storage candidate is screened under this plan.

## Decision and preservation

Report nearest-rank p50/p95/max and sum for `journal_finish` and each subphase,
plus CLI wall/translation execution, chat count and failures, separately by arm.
Use exact same operation counts and outcomes for paired speed comparison; otherwise
mark it non-comparable. A candidate is a supported improvement only if both
matched real candidate runs have lower journal-finish sum and median than their
paired baselines, the fixture median also falls, and durability/recovery checks
pass. Two runs cannot establish a stable tail estimate; report p95 descriptively.
If the cause or benefit remains uncertain, keep the current storage contract and
state that speedup is unproven.

## Declared measurement amendment, 15 October 2026

The first real run uses opt-in WAL header reads and exposes their observer cost.
Two additional fresh real baselines without those reads are now required to
measure the unperturbed phase distribution; this adds one real run but stays
within the original 45-minute probe budget and unchanged 32-cue/request limits.
The first Node harness launch failed before inference under child-process
sandboxing. Keep it in the failure inventory. A candidate comparison remains
conditional on an identified, safe storage cause; no speculative `synchronous`
change is permitted.

Keep `synchronous` unchanged. A request finish must commit before validated text
can be checkpointed; the checkpoint remains separately durable before progress is
acknowledged. Verify writer failure, restart/recovery, original source digest and
byte-identical offline re-export. Do not publish source, model response or local
private paths.
